# pico-deskflow-bridge

Pico 2 W (RP2350, default) / Pico W (RP2040) firmware: Deskflow client over USB CDC-NCM → BLE HID keyboard/mouse. See README.md.

- Independent crates, no root workspace. Run cargo from inside `deskflow-proto/` (host target, `cargo test`), `bootloader/` or `firmware/` (its `.cargo/config.toml` sets thumbv8m.main-none-eabihf; running from the repo root builds for the host and fails).
- Boards are cargo features, exactly one at a time: `pico2-w` (default, thumbv8m.main-none-eabihf) or `pico-w` (`cargo pico-w` alias = `--target thumbv6m-none-eabi --no-default-features --features pico-w`). Board differences live only in `firmware/src/board.rs` and `memory-rp2040.x`/`memory-rp2350.x` (picked by build.rs). The Pico 2 W runs at 200 MHz and 1.15 V (`board::config`, for TLS throughput), so the CYW43 SPI needs divider 4 to stay at the 25 MHz of `RM2_CLOCK_DIVIDER` at stock. Check both boards build and pass clippy.
- UF2s come from `scripts/elf2uf2.py` (elf2uf2-rs is RP2040-only); its RP2040 output must stay byte-identical to elf2uf2-rs (CI checks). RP2350 UF2s carry picotool's RP2350-E10 absolute block.
- Keep protocol/mapping logic in `deskflow-proto` (host-testable); `firmware` should only glue hardware to it.
- Dependency pins are deliberate: embassy rev 3cd51e6 + trouble rev 43a1441 are the pair trouble's rp-pico-w example builds against; embassy-crypto comes from embassy rev bd35bd7 because trouble-host pins it. Bump them together.
- trouble-host needs the `central` feature even though we're peripheral-only (upstream gating bug on `BdAddr`).
- Deskflow wire formats: upstream `src/lib/deskflow/ProtocolTypes.cpp`. macOS servers send key `button` = macOS virtual keycode + 1.
- Development may happen without hardware (a remote workspace, CI): build `.uf2` with `scripts/uf2.sh [pico2-w|pico-w]` and flash from a machine with the Pico attached.
- TLS: the `embedded-tls` provider/verifier lives in `deskflow-proto::tls`; `tests/openssl.rs` runs real handshakes against `openssl s_server` (skipped without openssl). Firmware enables `spin/portable_atomic` because rsa → num-bigint-dig → lazy_static needs CAS that thumbv6m lacks.
- Settings page: HTML/JS is `deskflow-proto/src/web/index.html` (embedded with `include_str!`); request parsing/validation in `deskflow-proto::{web, settings, auth, diag}`, socket glue in `firmware/src/web.rs`. Saving writes flash and restarts the Pico; settings are read only at boot. The optional password (flash key 5, applied live) is separate from the settings form so it never appears in `/api/state`.
- Clipboard is Mac → laptop only, typed as US-layout keystrokes (`deskflow-proto::{clipboard, typing}`, `firmware/src/clipboard.rs`); a HID keyboard can't reach the laptop's clipboard. Large `DCLP` chunks (up to 512 KiB) are streamed in `read_frame`, never buffered whole. The page's text box (`/api/clipboard`) streams into the same buffer, for servers whose clipboard doesn't reach us (Wayland).
- Code isn't rustfmt-default formatted (no `rustfmt.toml`); don't run `cargo fmt` over the tree. CI runs clippy with `-D warnings`, tests and the UF2 build; `TESTING.md` is the hardware checklist.
- Laptops: one active at a time, enforced by the controller's accept list (`firmware/src/ble.rs`); bonds keep their slots for the Ctrl+Alt+1…4 hotkeys (`deskflow-proto::{pairing, typing}`), the active one is flash key 6, and `Pair a new laptop` opens advertising for 2 minutes.
- Optional buttons/LEDs: shared model in `deskflow-proto::panel` (timing, patterns, actions), GPIO glue in `firmware/src/panel.rs`, which also runs the page's virtual presses. Nothing may depend on them being fitted.
- Firmware updates (Pico 2 W only): `bootloader/` is a third crate built on embassy-boot; its `memory.x` and `firmware/memory-rp2350.x` must agree. `scripts/uf2.sh` writes the full UF2 (with bootloader, for BOOTSEL) and `-update.uf2` (firmware alone, for the page); the UF2 reader is `deskflow-proto::uf2`, the rest `firmware/src/update.rs`. Firmware runs at 0x10021000, so a UF2 of the firmware alone won't boot from BOOTSEL. Write the update slot sector by sector: erasing it whole stalls USB.
- Mouse path: moves merge in one slot (`MOTION`) and go out while the controller holds fewer than two packets, or after two connection intervals (`firmware/src/flow.rs` wraps the HCI transport to see "packets sent" reports, since trouble hides its credits). Keep the firmware at `opt-level = 3`: software AES-GCM on core 1 is the throughput limit: at 150 MHz a fast mouse outran it, so moves backed up into TCP and long movements lagged. At 200 MHz it keeps up (backlog 425 B, TLS path 1.3 ms, on hardware). TLS off is the fallback.
- TLS runs on core 1 (`firmware/src/tls_offload.rs`): core 0 owns the network stack and pipes ciphertext over; every session is `start` → `handshake` → `PlainLink` → `stop`. Flash writes must stay on core 0 (embassy pauses core 1 for them). `tools/tls-offload-test` runs that module on the host (thread = core 1) against openssl; its build.rs rewrites the few hardware lines, so keep those `use` lines as they are or update it.
- Clipboard typing layouts: `deskflow-proto/src/layouts.rs` is generated by `tools/gen_layouts.py` from a pinned xkeyboard-config tag; don't edit it by hand (CI regenerates and diffs).
