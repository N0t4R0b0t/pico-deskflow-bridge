# Contributing

Thanks for looking. Bug reports, hardware results and pull requests are all
welcome. This is a hobby project run by one person, so replies may take a few
days.

## Reporting a problem

Open an issue and include:

* the board (Pico 2 W or Pico W) and the firmware version shown on the
  settings page;
* the Deskflow server's OS and version, and the laptop's OS;
* the log from the settings page (or the serial port) around the problem. It
  contains Bluetooth addresses and TLS fingerprints, so look it over first;
* what you expected, and what happened.

For a vulnerability, don't open an issue: see [SECURITY.md](SECURITY.md).

## Hardware results

[TESTING.md](TESTING.md) is the hardware checklist. A run on a board, server or
laptop the project hasn't seen, or any of the parts marked untested in the
README, is as useful as a code change.

## Working on the code

The crates are independent (no root workspace), so run cargo from inside each:

```sh
cd deskflow-proto && cargo test          # protocol, mapping, TLS (uses openssl if installed)
cd deskflow-proto && cargo clippy --all-targets -- -D warnings
cd firmware && cargo clippy --release -- -D warnings                      # Pico 2 W
cd firmware && cargo clippy --release --target thumbv6m-none-eabi \
    --no-default-features --features pico-w -- -D warnings                # Pico W
cd bootloader && cargo clippy --release -- -D warnings
cd tools/tls-offload-test && cargo run --release                          # core-1 TLS pipeline on the host
./scripts/uf2.sh [pico2-w|pico-w]                                         # build a UF2
```

Before opening a pull request, check that both boards build and pass clippy
(CI runs the same, with `-D warnings`).

Some conventions that aren't obvious from the code:

* Put protocol and mapping logic in `deskflow-proto`, where it can be tested on
  the host. `firmware` should only connect hardware to it.
* Board differences live in `firmware/src/board.rs` and the two
  `memory-*.x` files, and nowhere else.
* There is no `rustfmt.toml`, and the code isn't rustfmt-formatted. Please
  don't run `cargo fmt` over files you aren't otherwise changing.
* `deskflow-proto/src/layouts.rs` is generated by `tools/gen_layouts.py`; don't
  edit it by hand (CI regenerates it and compares).
* The embassy and trouble revisions in `firmware/Cargo.toml` are pinned as a
  pair on purpose, and move together.
* Settings page changes touch `deskflow-proto/src/web/index.html`; run
  `tools/screenshots.py` afterwards if the layout changed.

[CLAUDE.md](CLAUDE.md) has more detail on these and on the design decisions
behind them.

## Pull requests

Keep them focused, say what you tested (host tests, which board, which server
and laptop), and update the README or TESTING.md if behaviour changes. By
contributing, you agree your work is released under the [MIT license](LICENSE).

## Snapshots and releases

Every push to `main` that passes CI uploads a **snapshot** of the UF2s to
Cloudflare R2, overwriting the last one (`pico-deskflow-bridge/snapshot/`).
Pushing a tag like `v0.1.0` makes a **release**: a GitHub release with the
UF2s, and a copy kept in R2 (`pico-deskflow-bridge/releases/<tag>/`, plus
`releases/latest/` unless the tag has a suffix like `-rc1`). Each folder has a
`sha256sums.txt` and a `version.txt`.

The R2 job needs the repository variables `R2_BUCKET` and `R2_ENDPOINT` and the
secrets `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`; without them it stops at
its first step and says so.
